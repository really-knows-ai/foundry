- [x] Governance records git commit hash instead of content hash of cycle configuration — `computeGovernance` in `hash.js` now accepts an optional `cycleId` parameter and hashes `.foundry/cycles/<cycleId>.yaml` content instead of running `git rev-parse HEAD`. The `config_commit` field now holds a SHA-256 content hash of the cycle configuration file.
- [x] Appraise attestation never passes `appraiser_verdicts` — `appendAppraiseAttestation` in `executor-attestation.js:131-153` does not include `appraiser_verdicts` in the params forwarded to `appendStageAttestation`, so `appraiseStatus` in `stage-payload.js:116-122` always derives `'incomplete'` regardless of actual evaluation outcomes.
- [x] Human-appraise evaluations use `pass` (boolean) instead of `verdict` — `buildHumanEvaluations` in `executor-attestation.js:170-177` produces `{ appraiser, pass, completed }` but the `EvalEntry` schema in `stage-payload.js:23-27` expects `{ appraiser, verdict: 'passed'|'failed', completed }`.
- [x] `maybeSealRun` seals at end of each cycle, not end of run — `orchestrate-finalise.js:182-191` triggers on `isFinalStageOfCycle`, which is true at the end of every cycle. This produces multiple cycle attestation lines in multi-cycle runs rather than a single seal for the entire run.
- [x] `executeAppraise` does not call `appendAppraiseAttestation` when `setupAppraiseStage` returns an error — `prepareAppraiseContext` in `run-appraise.js:266-267` returns `{ error: ... }` without writing an attestation line when `setupAppraiseStage` fails (missing cycleId, cycle not found, no output-type).
- [x] False positive: implementation has six stage-execution paths across five stage types — `VALID_STAGES` in `stage-payload.js:54` correctly defines five stage names (assay, forge, quench, appraise, human-appraise). The six execution paths are: `executeForge` → `appendForgeAttestation`, `executeQuench` → `appendQuenchAttestation`, `executeAssay` → `appendAssayAttestation`, `executeAppraise` → `appendAppraiseAttestation`, `handleAlwaysHumanAppraise` → `appendHumanAppraiseAttestation`, and `handleDeadlockOverride` → `appendHumanAppraiseAttestation`. Two execution paths share the `human-appraise` stage type. This matches the spec's R2 ("six stage-execution paths") and AC #2. The five attestation helpers in `executor-attestation.js` are one per stage type, which is the correct design. No discrepancy exists between spec and implementation.
- [ ] Hash mismatch on stage lines: excluded from composite, not reported in seal result — `parseAttestationLines` in `hash.js:190-208` calls `handleMismatchLine` and `continue`s, permanently excluding mismatched lines. The spec says "the composite may still include it but the mismatch is reported." The `sealCycleAttestation` return value (hash.js:275-281) has no field indicating skipped or mismatched lines — mismatches are only logged to stderr via `console.warn`.
- [ ] No test verifies attestation file is committed in merge commit — Acceptance criterion 16 requires `.foundry/attestations/<run-id>.jsonl` is staged in the same merge commit as artefact changes, but no test asserts this.
- [ ] Governance key `workfile_hashes` naming mismatches spec terminology — The key stores law file hashes but is named `workfile_hashes` (`hash.js:105`). The spec describes "hashes of law files and cycle configuration."
